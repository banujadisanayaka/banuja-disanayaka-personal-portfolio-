PROJECT JOURNAL

Banu 2.0

2026 / Voice → actionExplore the system ↓

01 / THE CONTEXT

A voice conversation with a deliberate path to action.

A voice interface is a sequence of systems, not one model call. Audio must be received, transcribed and interpreted; a tool may be requested; the result must return to the conversation; and the answer must become speech. Failure in any one of those stages changes the whole experience.

The project explores that sequence as an explicit orchestration problem. The backend coordinates the turn, while the mobile client handles the user-facing interaction. The current system is designed around one user, which is an important boundary of the experiment.

The design question

A voice assistant becomes useful when it can do more than reply. It also becomes harder to trust when a conversation can trigger actions without clear limits.

02 / THE WORKFLOW

Follow the system.

Explore each stage to see how the parts connect.

01

Android → WebSocket

Bring the voice into the turn

The Flutter Android client communicates with the FastAPI backend over WebSockets. Speech recognition provides the text that the conversation layer can work with, separating the audio interaction from the reasoning and tool logic.

Wake-word handling and the conversational backend are distinct concerns. The repository describes client-side wake-word handling; a cloud server does not have access to a local microphone just because a microphone module exists in the codebase.

02

Transcription → model routing

Choose a response path

The backend connects the transcribed request with the model layer. The project explores local and cloud routing, making provider choice a backend concern rather than something every client screen needs to implement.

A local model option does not make the complete phone-to-server system fully offline. Connectivity, speech services and provider configuration still determine what can actually run in a given setup.

03

Bounded orchestration loop

Use explicitly defined tools

Tools have defined schemas and control logic. The conversation loop limits its rounds and uses a shared time budget, so one request cannot expand indefinitely into more model and tool calls.

A tool schema says what an action looks like; the application must still validate the request and handle failures. The implementation includes turn-state cleanup when execution fails rather than treating every partial turn as complete.

04

Tool result → spoken response

Return an understandable answer

Tool results can return to the conversation before the response is converted into speech. Keeping the turn coordinated on the backend provides one place to manage the handoff between model output, tool execution and audio.

The prototype also explores webcam-derived emotion context. That process-wide context is one reason the current backend must be described as single-user rather than as a service for unrelated users.

03 / THE EXPERIENCE

What the product needs to make clear.

01

Conversation can connect to an action

The tool layer creates a controlled vocabulary between a model’s proposed action and the application’s executable capabilities. It provides a place to inspect and bound that relationship.

02

A backend with responsibility for the whole turn

Speech, routing, tools and response generation have different failure modes. Central orchestration gives the interaction a shared lifecycle and budget.

03

Exploration with visible deployment limits

The repository records production-secret requirements, origin configuration and persistence concerns. Those details matter when an experiment moves from a laptop to a hosted backend.

04 / UNDER THE SURFACE

How the architecture supports the idea.

FastAPI · Python · Flutter · WebSockets

FastAPI + Python

The backend coordinates speech recognition, model calls, tool execution and text-to-speech. The control layer defines the actions the loop understands.

Flutter + WebSockets

The Android client is a separate interface connected to the conversation backend, allowing the interaction layer and orchestration to develop independently.

Local and cloud model paths

Routing experiments include local inference and hosted providers. The available path depends on the configured environment; it is not a promise of universal offline operation.

Personal state and persistence

The documented memory files require durable storage on an ephemeral host. Process-wide visual context also needs redesign before a multi-user architecture would be appropriate.

05 / THE NEXT CHAPTER

What matters from here.

The useful design question is not only “can the assistant do this?” It is also how a turn ends, how a failed action is explained and what information belongs to this user. Boundaries are part of the product experience.

The next validation should examine complete turns on a real phone: interrupted audio, slow providers, failed tools, reconnection and persisted personal state. Banu 2.0 remains an experimental single-user system, with those concerns clearly separated from a future public service.

Where it stands

The current architecture is single-user and includes experimental vision context and local/cloud model routing. It is not presented as a multi-tenant service or a fully offline mobile assistant.
