THE PROBLEM

A real starting point.

A voice assistant becomes useful when it can do more than reply. It also becomes harder to trust when a conversation can trigger actions without clear limits.

THE APPROACH

Make the relationships clear.

Banu 2.0 connects speech recognition, a model and text-to-speech through a Python backend and a Flutter client. The tool loop has an explicit turn budget and a limited number of rounds.

DESIGN DECISIONS

01

Bound the conversation loop

The backend caps tool rounds and uses a shared turn budget so one request cannot grow into an open-ended chain.

02

Define the available actions

Tool schemas and control logic form the boundary between a model’s suggestion and an action the application understands.

03

Separate client and orchestration

A WebSocket connection carries the interaction while the backend coordinates speech, model routing and tools.

Where it stands

The current architecture is single-user and includes experimental vision context and local/cloud model routing. It is not presented as a multi-tenant service or a fully offline mobile assistant.
