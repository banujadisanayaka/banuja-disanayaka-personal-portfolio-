PROJECT JOURNAL

01 / THE CONTEXT

An everyday workspace with a record you can trace.

A spreadsheet is familiar and useful, but routine administration becomes harder when someone must navigate rows, formulas and separate attendance or payment records to answer a simple question. The product gives those tasks an interface built around students and classes.

The design challenge goes beyond adding forms. A payment can be partial. Attendance can be entered incorrectly. Two browser sessions can open the same record before either saves. The application needs to distinguish a new entry from a correction and make the state of each write clear to the administrator.

The design question

A tuition administrator needs a clear view of students, attendance and fees without having to operate a spreadsheet directly. Mistakes must be correctable, and corrections must not quietly overwrite someone else’s work.

02 / THE WORKFLOW

Follow the system.

Explore each stage to see how the parts connect.

01

Student → permanent identity

Establish the student record

Student creation assigns a permanent identifier and connects the student with class enrolment information. Duplicate detection helps catch repeated entry before another record is created. The student profile brings related information into one place.

Names are useful for people, but a permanent identifier is the safer connection between student, attendance and payment records. A change in display information should not create a different student.

02

Roster → validated entry

Record attendance and fees

Class rosters support batch attendance recording. Payment transactions support partial payments and guard against overpayment in the documented implementation. These are distinct administrative actions with their own validation.

A write travels through a Netlify Function to the Sheet. The interface must not report success merely because it changed something locally while the underlying write failed.

03

Record version + reason

Correct without losing context

Correction flows ask for a reason and carry the version of the record that the administrator opened. If the source has changed, a stale correction is rejected so the current information can be loaded before trying again.

This is optimistic concurrency: two people can read the same record, but the second save should not silently replace the first. An explicit conflict is more useful than an apparently successful lost update.

04

Saved records → reports

Review the history

Student profiles, history and reports bring the underlying records back into the web workspace. They help an administrator review what was recorded and understand changes without switching to raw spreadsheet rows for every task.

Reporting is only as reliable as the records underneath it. Audit information and clear correction behaviour support the report; they are not decorative extras added after the main screens.

03 / THE EXPERIENCE

What the product needs to make clear.

01

Student-centred administration

Permanent IDs, enrolment information, duplicate checks and student profiles organise the work around a person. Attendance and fees can then refer to the same record consistently.

02

Payment detail that reflects real administration

A fee is not always paid in one transaction. Partial payments, correction and voiding paths make the model more useful than a single paid/unpaid switch.

03

Server-owned business writes

Google credentials remain on the server. The browser sends a request; the backend checks it and performs the Sheets operation. Failed writes must remain visible as failures.

04 / UNDER THE SURFACE

How the architecture supports the idea.

React · TypeScript · Google Sheets · Netlify Functions

React + TypeScript + Vite

The frontend contains the administration shell, student forms, profiles and dedicated attendance, payment, report and history views.

Netlify Functions

Endpoints validate inputs and coordinate student, attendance and payment operations. Correction endpoints retain reasons and guard against stale record versions.

Google Sheets as authority

A server-side service account talks to the Sheets API. The documented write engine uses explicit row operations, keeping business records in the agreed workbook structure.

Authentication boundary

The development authentication path is restricted to staging. Production identity and access configuration must be completed and validated before a client launch.

05 / THE NEXT CHAPTER

What matters from here.

The most meaningful design work is often in the uncomfortable states: a duplicate, a rejected correction, an interrupted save or a payment that does not match the expected amount. Giving those states clear language is part of making the tool approachable.

The next release gate is production identity configuration followed by an end-to-end administrator trial against the intended workbook. The repository is active development, and the case study does not present it as an independently audited, launched school service.

Where it stands

The repository still contains a development authentication path. Production Google identity and access configuration must be completed and validated before a client launch.

Evidence behind this story

Reviewed attendance correction and report endpoints, Sheets integration, student profile components and the application shell.
