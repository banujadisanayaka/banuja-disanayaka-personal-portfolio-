01 / THE CONTEXT

A knowledge system that begins with your own files.

Capturing an idea is easy. Keeping it useful as a collection grows is harder. Notes acquire links, structure and context; titles change; files move. A knowledge tool should help with that complexity without making the application the only way to reach the original material.

Second Brain starts from a local vault containing Markdown and structured metadata. The application can add richer editing and discovery around those files, but the stored thought should remain understandable outside the interface. That choice shapes the editor, the identity model and the graph.

The design question

Notes become less useful when they are trapped in one application or disconnected from the work they support. I wanted a knowledge workspace that starts with ownership of the files themselves.

02 / THE WORKFLOW

Follow the system.

Explore each stage to see how the parts connect.

01

Content + stable identity

Capture a knowledge object

The workspace models notes and related knowledge objects with stable identifiers. A title helps a person recognise an object; its identity provides a reliable reference when it is renamed, moved or linked elsewhere.

The reviewed build work includes template selection, editor flows and structured linking. The aim is to make capture approachable while keeping a consistent object model underneath it.

02

Markdown + frontmatter

Write to the local vault

The vault writer is the persistence boundary. Text and metadata are written to the local files, so the vault remains the canonical record of the knowledge rather than a disposable export produced by a database.

Frontmatter round trips, external edits and Android storage permissions are real engineering concerns. Preserving what is already on disk matters as much as making a new note look correct in the editor.

03

Files → rebuildable SQLite

Build a useful index

SQLite supports discovery and relationships around the vault. Its role is to make the local material easier to query and navigate, with rebuild and repair paths that recover the derived structures from the durable source.

A rebuildable index separates convenience from ownership. Deleting a cache should not delete the only copy of someone’s thinking.

04

Explicit links → graph view

Explore the connections

The graph provider builds a view over stored relationships. The reviewed graph work separates the engine from the screen and bounds the additional similarity calculations as the collection grows.

Explicit links and inferred similarity answer different questions. The architecture keeps the recorded relationship model separate from an optional suggestion that two objects may be related.

03 / THE EXPERIENCE

What the product needs to make clear.

01

Writing and structure in the same workspace

The reviewed editor work includes rich editing, source mode, formatting and identity-aware wiki links. Those interactions sit on top of the file format instead of replacing it with an opaque document store.

02

Relationships that survive routine changes

Stable object identity is designed to preserve links through rename and move operations. The project’s validation work also covers hierarchy, deletion and restoration.

03

A graph that can grow with the vault

The provider separates relationship computation from rendering. Bounded similarity work and performance fixtures address the cost of comparing large collections.

04 / UNDER THE SURFACE

How the architecture supports the idea.

React Native · Expo · TypeScript · Markdown · SQLite

React Native + Expo

The mobile interface and Android-first workflows shape capture, editing and navigation. This is an application prototype, not a browser-only notes page.

Markdown + YAML metadata

The vault stores readable content and structured properties. Compatibility and careful round trips matter because those files may be used outside this application.

SQLite and relationship records

Derived indexes and explicit edges support discovery and graph views. Rebuild and repair behaviour help keep those structures connected to the vault.

GraphProvider boundary

The provider exposes graph data independently of the screen. The reviewed project state records the provider and performance harness as landed, with later graph work still in progress.

05 / THE NEXT CHAPTER

What matters from here.

Ownership is an architectural decision. An export button helps, but it is different from making portable files the source of truth throughout the product. That decision creates more engineering work around identity and storage, and it is the core of this project.

The recorded Android storage-access fix still requires device verification, and the larger graph programme is unfinished. The next valuable proof is reliable capture, edit and recovery on an actual device, alongside a graph that stays useful as the vault grows.

Where it stands

The project state records graph work in progress and Android storage-access verification still to complete. This is a prototype, not a published app-store release.
