CASE STUDY / 04

BANU 2.0

A single-user voice assistant system connecting speech, an agent tool loop, text-to-speech, memory and context through a mobile client and backend gateway.

BACKEND

01 / SYSTEM

Voice is only the interface layer.

The repository describes an end-to-end assistant where speech-to-text feeds an LLM agent loop with tools, the result returns through text-to-speech, and webcam-driven emotion context can influence the process. A Flutter Android client communicates with the FastAPI backend over WebSockets.

02 / SECURITY

Production mode is designed to fail closed.

The current deployment notes explicitly require strong JWT and device secrets in production, restrict CORS to configured client origins, and use 24-hour JWT expiry. These constraints are important because an assistant that can call tools should not treat authentication as a cosmetic layer.

Strong production secrets

The backend refuses to start in production unless required secrets satisfy its strength expectations.

Origin control

Wildcard CORS is reserved for non-production environments rather than becoming the production default.

03 / AUDIT FINDINGS

Architecture also means documenting what is not safe yet.

  • 01Persistent memory and OAuth state currently live under local data files, so ephemeral hosts require a mounted disk or database to avoid state loss on restart.
  • 02The system is intentionally single-tenant. Emotion/blendshape context is process-wide and should not serve multiple users without per-session isolation.
  • 03Reminder timing is explicitly tied to a configured timezone rather than assuming server-local time.
  • 04Wake-word detection is handled client-side for cloud deployment because the backend wake-word module depends on a local microphone.

SOURCE OF TRUTH: verified against the current private Banu 2.0 repository README. Security and deployment caveats are intentionally included rather than hidden; they show the current system boundary.

04 / PRODUCT PRINCIPLE

Capability without boundaries is technical debt.

This project is useful as a systems case study because it treats limitations as part of the design: tenancy, persistence, authentication and deployment context are explicit architectural decisions rather than post-launch surprises.
