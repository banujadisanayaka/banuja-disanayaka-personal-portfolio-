CASE STUDY / 02

CLASS TRACKER TDG

A business application designed around a simple requirement: make tuition-class administration usable for non-technical operators without weakening data integrity.

ROLE

Product Owner · Systems Designer

FRONTEND

React · TypeScript · Vite

BACKEND

Netlify Functions

DATA

Google Sheets as authoritative store

01 / PROBLEM

Business software has to survive real mistakes.

The product is built for attendance, student records and fee operations where duplicate saves, corrections, stale edits and ambiguous write outcomes can damage trust. The architecture therefore treats the Google Sheet as the authoritative business-data store and deliberately avoids client-side credentials or fake offline-success states.

Write-through discipline

Successful UI feedback follows authoritative server-side writes rather than optimistic local fallbacks.

Correction accountability

Attendance and payment flows include correction handling, duplicate prevention and audit-oriented behavior.

02 / ARCHITECTURE

Thin client. Server-held credentials. Explicit writes.

The current staging architecture separates the responsive React interface from Netlify Functions, while server-side service-account JWT handling communicates with Google Sheets. The repository documents exact-row and insert-row write logic rather than raw append-cell behavior.

03 / IMPLEMENTED

The build already handles more than CRUD.

  • 01Permanent student IDs, duplicate detection, class enrollment and Audit Log integration.
  • 02Today-class and roster APIs plus batch attendance saving with session creation and duplicate prevention.
  • 03Payment transactions with partial payments, overpayment protection, corrections and voiding.
  • 04Reusable normalized dropdown values so operational input becomes more consistent over time.
  • 05Fail-closed authentication/config behavior for staging instead of silently running insecurely.

SOURCE OF TRUTH: verified against the current Class Tracker repository. Planned modules are intentionally not presented here as completed features.

04 / PRODUCT PRINCIPLE

Complexity belongs in the system, not on the user.

The strongest design constraint is operational: the administrator should be able to run the business from the website even if their technical confidence is low. That shifts design effort toward predictable flows, readable status, safe correction paths and clear system feedback.
